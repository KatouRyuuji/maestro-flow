## 1. Global Overview

### Scopes

| Path | Scope | Description |
|------|-------|-------------|
| `.workflow/` | Project-level | All workflow state for the current project |
| `~/.maestro/` | Global-level | Cross-project templates, configs, overlays |
| `.workflow/collab/` | Team-level | Human team collaboration, strictly isolated from `.workflow/.team/` (Agent bus) |

### Core Principles

- `.workflow/` is added to `.gitignore` and excluded from version control (`project.md` as optional exception)
- All artifact paths are relative to the `.workflow/` root directory
- Each directory/file has a single responsibility with no overlapping storage
- All command outputs are registered through `state.json.artifacts[]`, enabling cross-phase tracking

## 3. Core File Details

| File | Purpose | Key Fields |
|------|---------|------------|
| `state.json` | Project state machine + Artifact Registry | `version`, `status`, `current_milestone`, `current_phase`, `artifacts[]`, `milestones[]`, `milestone_history[]` |
| `config.json` | User workflow config (created by `maestro-init`) | `granularity`, `workflow_agents`, `gate_preferences` |
| `project.md` | Project definition (created by `maestro-init`) | Core Value, Requirements, Key Decisions, Context |
| `roadmap.md` | Milestone/phase roadmap (created by the `roadmap` command / `/maestro` roadmap chain) | Milestone list, success criteria, dependencies, Phase Progress Table |
| `wiki-index.json` | Wiki unified index (auto-generated by WikiIndexer) | Indexes project/specs/knowhow/issues/roadmap |

### state.json Schema

```json
{
  "version": "3.0",
  "status": "idle|active",
  "current_milestone": "M1",
  "current_phase": 1,
  "milestones": [{ "id": "M1", "status": "active|completed|forked", "phases": [1, 2] }],
  "milestone_history": [{ "milestone_id": "M1", "completed_at": "ISO-8601" }],
  "artifacts": [{ "id": "ANL-001", "type": "analyze", "path": "scratch/...", "status": "completed" }]
}
```

```json

  "id": "ANL-001",
```

## 6. Session/Run Model (v0.5.56+)

Maestro and Ralph share the same **canonical Session/Run chain protocol** (schema `session/1.3`):

- A **Session** is the topic grouping and index; `session.json.orchestration` is the single source of truth for chain / goal / decision.
- A **Run** is a single execution attempt; a Run's outputs, handoff, gate, proposal, and transition receipt belong to that Run.
- The orchestration layer invokes `maestro session ...` (next/done/decide/seal/status/resolve/resume/chain insert·skip·replace/meta update), while the execution layer invokes `maestro run ...` (brief/check/create/prepare).
- Protocol files are always written by the Runtime; prompts never write session.json/run.json directly.

### Directory Layout

```
.workflow/sessions/{session-id}/
├── session.json          # Session state machine (session/1.3)
├── evidence/             # Evidence Registry
└── runs/{run-id}/
    ├── outputs/          # Authoritative artifacts
    ├── evidence/         # Informal diagnostic traces
    └── report.md         # handoff
```

### session.json Core Structure

```json
{
  "schema": "session/1.3",
  "session_id": "maestro-fix-login",
  "intent": "Fix the login chain",
  "status": "running|paused|sealed|archived|failed",
  "orchestration": {
    "engine": "ralph|coordinator|manual",
    "quality_mode": "quick|standard|full",
    "auto_mode": false,
    "position": { "current_step": 2 },
    "chain": [
      { "command": "analyze", "args": "--session {session}", "stage": "analyze", "goal_ref": "G1", "status": "completed" },
      { "command": "post-execute", "stage": "execute", "decision_ref": "post-execute", "status": "pending" }
    ],
    "decision_points": [{ "point_id": "post-execute", "max_retries": 2 }],
    "decomposition": {
      "goals": [{ "id": "G1", "goal": "...", "done_when": "...", "lifecycle": ["execute", "review"], "status": "pending" }]
    }
  },
  "boundary_contract": { "in_scope": [], "out_of_scope": [], "constraints": [], "definition_of_done": "" }
}
```

- `engine` is a compatibility persistence field, not a Session type or strategy
- An execution step has only `command/args?/stage?/goal_ref?/retry_max?`; a decision step declares `decision_ref`
- Chain advancement is **verdict-driven**: execution steps use `maestro session done --verdict`, decision steps use `maestro session decide --verdict`

### Evidence Registry

`maestro session evidence [session-id]` queries the canonical Evidence Registry, supporting `--kind` / `--status proposed|accepted|rejected|superseded` / `--run` / `--point` filters. Evidence is stored as typed entries and resolved to concrete Artifact references; `chain-proposal/1.0` is automatically discovered and validated by `maestro run check`.

### Artifact Output Paths

Run artifacts are uniformly written to the `outputs/` directory, while `evidence/` is demoted to informal traces:

| Directory | Positioning | Authority |
|-----------|-------------|-----------|
| `runs/{run-id}/outputs/` | Artifact output (report.md, plan.json, etc.) | Authoritative, consumed downstream |
| `runs/{run-id}/evidence/` | Debug/diagnostic traces | Informal, for retrospection only |

Sealed outputs within the same Session are reused only via the canonical `upstream` of the birth packet / brief; context is never rebuilt manually.

### Session Naming and Creation

`maestro session create` / `maestro session start` support explicit naming via `--id <slug>`:
- Valid characters: `a-z`, `0-9`, `-`
- Invalid input automatically falls back to an ASCII slug
- When unspecified, it is automatically slugified from the intent/topic

```bash
maestro session start "修复登录链路" --chain analyze plan execute review   # Human entry point
maestro session create "修复登录链路" --id maestro-fix-login --chain-file chain.json   # Orchestrator builds the chain
```

### legacy Migration (session migrate)

v0.5.56 merges Maestro and Ralph into a single Session chain protocol. The old `.workflow/.maestro/ralph-*/status.json` and `ralph-meta.json` are folded into `sessions/{id}/session.json` via `maestro session migrate [--session <id>]` and marked with `session/1.3` (idempotent).

### chains Data Layer Removal

v0.5.50+ removed the coordinate graph execution subsystem (the chains data layer). The former coordinate `--chain` parameter is no longer needed; full chain orchestration has moved to the `maestro session` model.

## 7. Milestone Archives

When a milestone is completed, `/maestro-session-seal` creates an archive:

1. `/maestro-session-seal` validates completeness → `audit-report.md`
2. scratch artifacts are moved into `milestones/{M}/artifacts/`
3. `state.json.artifacts[]` entries are moved into `milestone_history[]`
4. knowhow is extracted, advancing to the next milestone

## 8. Naming Convention Quick Reference

### Scratch Directories

**Format**: `{YYYYMMDD}-{type}[-P{N}|-M{N}]-{slug}`

| Component | Values | Description |
|-----------|--------|-------------|
| `{YYYYMMDD}` | Date | Chronological sorting |
| `{type}` | analyze, plan, verify, review, debug, test, auto-test, brainstorm, collab, ui-design | Artifact type |
| `P{N}` / `M{N}` | P1, M1, etc. | Phase / Milestone scope (omitted for adhoc/standalone) |
| `{slug}` | kebab-case | Content summary |

### Artifact Types and Commands

| Type | ID Prefix | Scope | Command (via `/maestro` chain or Skill) |
|------|-----------|-------|------|
| analyze | ANL-{NNN} | phase, adhoc, standalone | `analyze` (`/maestro "分析..."`) |
| plan | PLN-{NNN} | phase, adhoc | `plan` (`/maestro "plan phase N"`) |
| execute | EXC-{NNN} | phase | `execute` (`/maestro "execute"`) |
| verify | VRF-{NNN} | phase, milestone | (retired; integrated into `/maestro-ralph` decision gate `post-execute`) |
| review | REV-{NNN} | phase | `review` (`/maestro "review"`) |
| debug | DBG-{NNN} | phase, standalone | `/maestro-odyssey --mode debug` |
| test | TST-{NNN} | phase | `test` (`/maestro "<test intent>"`) or `/maestro-odyssey --mode security` |
| brainstorm | BRN-{NNN} | adhoc | `brainstorm` (`/maestro "brainstorm..."`) |
| collab | CLB-{NNN} | adhoc | `collab` (`/maestro "collab..."`) / team chain |
| ui-design | — | phase, scratch | `/maestro-impeccable --codify` |

### Session ID Formats

| Type | Format | Example |
|------|--------|---------|
| maestro main session | `maestro-{slug}` or `maestro-{YYYYMMDD-HHmmss}` | `maestro-fix-login` |
| ralph session | `{slug}` / `{YYYYMMDD-HHmmss}` (unified Session chain, no longer distinguished by prefix) | `ralph-20260513-143022` (legacy) |
| player session | `player-{YYYYMMDD-HHmmss}` | `player-20260513-143022` |
| delegate ID | `{prefix}-{HHmmss}-{rand4}` | `gem-143022-a7f2` |
| Issue ID | `ISS-XXXXXXXX-NNN` | `ISS-a1b2c3d4-001` |
